# Deploy the Community Edition using an obd configuration file

This topic describes how to deploy the Community Edition of OceanBase Database using an obd configuration file. It covers the preparation of resources and configuration before deployment, as well as the steps to quickly deploy a distributed cluster.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>obd supports deploying both the Community Edition and Enterprise Edition of OceanBase Database. This topic uses the Community Edition as an example to illustrate the process of deploying OceanBase Database using an obd configuration file.</p>
</main>

## Server configuration

The server configuration used in this example is as follows:

| Category | Configuration |
| ---- | ---- |
| Number of servers | 4 |
| CPU | 8 cores x86_64 |
| Operating system | CentOS Linux release 8.5.2111 |
| Kernel | 4.18.0-348.7.1 |
| Available memory | 32 GB |
| Disk | SSD storage, with 196 GB for the installation directory, 2 TB for the log directory, and 2 TB for the data directory. |

<main id="notice" type='explain'>
  <h4>Note</h4>
  <ul>
  <li><p>In a production environment, the server must meet the minimum resource requirements (4 cores and 16 GB of memory). For long-term use, the available memory should not be less than 32 GB. Note that the memory limit refers to the value in the <code>available</code> column of the output of the <code>free -g</code> command. </p></li>
  <li><p>In environments with fewer CPU cores, the default minimum CPU_Count set by obd is 8. A low CPU core count can negatively impact the performance of OceanBase Database. </p></li>
  </ul>
</main>

### Deployment mode

This example uses a three-replica deployment mode. We recommend using four servers, and you can choose an appropriate deployment mode based on your specific situation. The usage of the four servers is as follows:

|     Role      |                Server                |                   Remarks                    |
| ------------- | ---------------------------------- | ----------------------------------------- |
| obd           | 10.10.10.4                         | The automated deployment software installed on the control server.            |
| OBServer node | 10.10.10.1                         | OceanBase Database Zone1                    |
| OBServer node | 10.10.10.2                         | OceanBase Database Zone2                    |
| OBServer node | 10.10.10.3                         | OceanBase Database Zone3                    |
| ODP (also known as OBProxy)          | 10.10.10.1, 10.10.10.2, 10.10.10.3                         | The proxy server for OceanBase Database.        |
| OBAgent       | 10.10.10.1, 10.10.10.2, 10.10.10.3 | The monitoring and data collection framework for OceanBase Database.              |
| obconfigserver | 10.10.10.4                        | Provides metadata registration, storage, and query services for OceanBase Database. |
| Prometheus    | 10.10.10.4                         | An open-source service monitoring system and time series database that provides a general data model and quick data collection, storage, and query interfaces. |
| Grafana       |  10.10.10.4    | An open-source data visualization tool that can visualize various metrics from data sources to help you better understand the system's running status and performance metrics. |

## Check the server's software and hardware configurations

Before deploying OceanBase Database, you must check the software and hardware configurations of the server where OceanBase Database is deployed.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>You must perform the following checks on each OBServer node. </p>
</main>

### Hardware requirements

#### Check whether the CPU supports the AVX instruction

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>This restriction applies only to servers with x86 architecture. If you are using a server with a different architecture, you can ignore this section.</p>
</main>

OceanBase Database requires that the CPU supports the AVX instruction. You can run the following command to check whether the CPU supports the AVX instruction.

```shell
lscpu | grep Flags | grep avx
```

#### Check the memory

Run the following command to check whether the available memory meets the requirements specified in the [Software and hardware requirements](https://en.oceanbase.com/docs/common-oceanbase-database-10000000001971619) section of the OceanBase Database documentation.



If the memory size does not meet the requirements, you can run the following command to clear the Linux cache, including PageCache, dentries, and inodes.

```shell

# or
```

## Pre-deployment configuration

To ensure the smooth installation and better usage of OceanBase Database Community Edition, the following configurations need to be performed before deployment.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>The following configurations need to be performed on each OBServer node. </p>
</main>

### Directory planning

When you deploy OceanBase Database Community Edition, you must plan the following three directories. The file system type must be XFS or EXT4.

* Installation directory: the directory where OceanBase Database software and system logs are stored. The space must be at least 25 GB.
* Log directory: the directory where OceanBase Database logs are stored. The space must be at least twice the size of the memory. We recommend that you configure the space to be at least three times the size of the memory.
* Data directory: the directory where data is stored. The space must be at least twice the size of the memory. The space depends on the size of the data to be stored.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>If the capacity of a directory in a mount point exceeds 16 TB, only the XFS file system is supported. </p>
</main>

To ensure the stability of the system, we recommend that you use different physical disks for the installation directory, log directory, and data directory. If physical resources are limited, OceanBase Database also supports the data directory and log directory being stored on the same disk. However, we do not recommend this configuration for business scenarios with high write pressure.

The following table describes the IOPS requirements for the disks.

| Scenario | IOPS requirement |
| --- | --- |
| The installation directory, log directory, and data directory are stored on different disks. | Each disk must have an IOPS of at least 1000. |
| The installation directory, log directory, and data directory are stored on the same disk. | The disk must have an IOPS of at least 3000. |

### Configure clock synchronization

When deploying a distributed OceanBase cluster, it is essential to ensure that all machines within the cluster are synchronized in time. Otherwise, the cluster will fail to start, and services will experience anomalies during operation. The allowed time deviation in an OceanBase cluster must not exceed 2 seconds. If the deviation exceeds 2 seconds, a leaderless state will occur. After restoring clock synchronization, restarting the OceanBase cluster can restore normal operation.

<main id="notice" type='explain'>
   <h4>Note</h4>
   <p>The following example demonstrates the process on a single machine. You need to follow these steps to configure clock synchronization for all machines in the cluster.</p>
</main>

1. Install the chrony service

   ```shell
   [root@test001 ~]# yum -y install chrony
   ```

2. Configure the chrony file

   ```shell
   [root@test001 ~]# vim /etc/chrony.conf
   ```

   Here is an example configuration:

   ```conf
   # Use Alibaba NTP server
   # Public NTP
   # Alicloud NTP
   ## Synchronize time using multiple NTP servers provided by Alibaba Cloud to enhance the reliability and fault tolerance of time synchronization.
   ## minpoll 4 sets the minimum synchronization interval between the NTP client and server to 16 seconds (when the time deviation is small).
   ## maxpoll 10 sets the maximum synchronization interval between the NTP client and server to 1024 seconds (when the time deviation is large).
   ## iburst indicates that four NTP packets will be sent quickly (every 2 seconds) upon initial or reconnection to accelerate time synchronization and reduce the initial synchronization time deviation.
   server ntp.cloud.aliyuncs.com minpoll 4 maxpoll 10 iburst
   server ntp.aliyun.com minpoll 4 maxpoll 10 iburst
   server ntp1.aliyun.com minpoll 4 maxpoll 10 iburst
   server ntp1.cloud.aliyuncs.com minpoll 4 maxpoll 10 iburst
   server ntp10.cloud.aliyuncs.com minpoll 4 maxpoll 10 iburst
   server ntp11.cloud.aliyuncs.com minpoll 4 maxpoll 10 iburst
   server ntp12.cloud.aliyuncs.com minpoll 4 maxpoll 10 iburst
   server ntp2.aliyun.com minpoll 4 maxpoll 10 iburst
   server ntp2.cloud.aliyuncs.com minpoll 4 maxpoll 10 iburst
   server ntp3.aliyun.com minpoll 4 maxpoll 10 iburst
   server ntp3.cloud.aliyuncs.com minpoll 4 maxpoll 10 iburst
   server ntp4.aliyun.com minpoll 4 maxpoll 10 iburst
   server ntp4.cloud.aliyuncs.com minpoll 4 maxpoll 10 iburst
   server ntp5.aliyun.com minpoll 4 maxpoll 10 iburst
   server ntp5.cloud.aliyuncs.com minpoll 4 maxpoll 10 iburst
   server ntp6.aliyun.com minpoll 4 maxpoll 10 iburst
   server ntp6.cloud.aliyuncs.com minpoll 4 maxpoll 10 iburst
   server ntp7.cloud.aliyuncs.com minpoll 4 maxpoll 10 iburst
   server ntp8.cloud.aliyuncs.com minpoll 4 maxpoll 10 iburst
   server ntp9.cloud.aliyuncs.com minpoll 4 maxpoll 10 iburst

   # Ignore stratum in source selection.
   stratumweight 0.05

   # Record the rate at which the system clock gains/losses time.
   ## Calculate the ratio of time gain or loss of the server based on actual time and record it to /var/lib/chrony/drift. This will allow the system to make the best time compensation adjustment upon reboot.
   driftfile /var/lib/chrony/drift

   # Enable kernel RTC synchronization.
   ## Enable kernel mode where the system time is copied to the Real-Time Clock (RTC) every 11 minutes.
   rtcsync

   # In the first three updates, adjust the system clock instead of slewing it if the adjustment is larger than 10 seconds.
   makestep 10 3

   # Allow NTP client access from the local network.
   #allow 192.168/16

   # Listen for commands only on localhost.
   bindcmdaddress 127.0.0.1
   bindcmdaddress ::1

   # Disable logging of client accesses.
   noclientlog

   # Send a message to syslog if a clock adjustment is larger than 0.5 seconds.
   logchange 0.5

   ## Specify the directory for log files.
   logdir /var/log/chrony
   #log measurements statistics tracking
   ```

   Set it to start on boot:

   ```shell
   [root@test001 ~]# systemctl enable chronyd
   ```

   ```shell
   [root@test001 ~]# systemctl start chronyd
   ```

4. Force time synchronization

   Run the following command only after the initial configuration to force a time synchronization.

   ```shell
   [root@test001 ~]# chronyc makestep
   ```

   ```shell
   [root@test001 ~]# chronyc tracking
   ```
