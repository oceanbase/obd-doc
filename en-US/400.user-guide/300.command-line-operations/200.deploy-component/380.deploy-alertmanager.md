# Deploy Alertmanager

This topic describes how to deploy Alertmanager by using an obd configuration file in a CentOS 7.9 x86 Linux environment.

## Prerequisites

* Install obd V3.6.0 or later. We recommend that you install the latest version. For more information, see [Install obd](../../../200.quick-start/100.install-obd.md).

* The obd image library contains the installation packages of the required components, such as OceanBase Database, OBAgent, Prometheus, and Alertmanager.

  If the obd server can connect to the Internet, the required components are automatically downloaded from the remote image library.

* When you deploy the system on an x86 server, make sure that the OBServer nodes support the AVX instruction set. Run the `lscpu | grep Flags | grep avx` command to check whether the AVX instruction set is supported.

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>When you deploy the system on an x86 server, if the OceanBase Database version to be deployed is in the following list, there is no need to check whether the server supports the AVX instruction set:</p>
    <ul>
    <li>V4.2.5.6 or later for V4.2.x.</li>
    <li>V4.3.5.4 or later for V4.3.x.</li>
    <li>V4.4.1.0 or later for V4.4.x.</li>
    </ul>
  </main>

* In an offline deployment scenario, when you deploy the system on an ARM server, make sure that the OBServer nodes support the LSE instruction set. Run the `lscpu | grep Flags | grep atomics` command to check whether the LSE instruction set is supported. If the server does not support the LSE instruction set, download the OceanBase Database installation package with the `nonlse` option and use the `obd mirror clone` command to upload the installation package to the local image library of obd.

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>The OceanBase All in One package does not contain the OceanBase Database installation package with the <code>nonlse</code> option.</p>
  </main>

## Procedure

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>This topic assumes that the server can access the public Internet or has the required software (such as OceanBase Database, OBAgent, Prometheus, and Alertmanager) installed. </p>
</main>

### Step 1: Modify the configuration file

If you installed obd by directly downloading it, you can view the sample configuration file provided by obd in the `/usr/obd/example` directory.

If you installed obd by decompressing the all-in-one installation package, you can view the sample configuration file provided by obd in the `~/.oceanbase-all-in-one/obd/usr/obd/example` directory.

For more information about the differences between the sample configuration files, see [Obtain a sample configuration file](../100.configuration-file-description.md) in the **Obtain a sample configuration file** section. Choose a configuration file based on your resource conditions.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>At the end of this topic, you will find a complete <a href="#sample-configuration-file">sample configuration file</a>. You can directly copy and modify it as needed.</p>
</main>

1. Create a configuration file

   ```shell
   [admin@test001 ~]$ vim alertmanager.yaml
   ```

2. Modify the user information

   ```yaml
   ## Only need to configure when remote login is required
   user:
     username: admin
   #   password: your password if need
     key_file: /home/admin/.ssh/id_rsa
   #   port: your ssh port, default 22
   #   timeout: ssh connection timeout (second), default 30
   ```

   `username` is the username for logging in to the target machine (the machine where OceanBase Database is installed). Ensure that your username has read and write permissions for the following paths. `password` and `key_file` are both used to verify the user. In most cases, you only need to fill in one of them.

   <main id="notice" type='notice'>
     <h4>Notice</h4>
     <p>After configuring the key path, if your key does not require a password, comment out or delete <code>password</code> to avoid it being considered the key password for login, which could lead to verification failure.</p>
   </main>

3. Configure OceanBase Database

   Modify the machine's IP address, port, and related directories, and configure memory-related parameters and the user password for the sys tenant.

   <main id="notice" type='explain'>
     <h4>Note</h4>
     <p>obd supports deploying OceanBase Database Enterprise Edition. This example deploys OceanBase Database Community Edition.</p>
   </main>

   ```yaml
   oceanbase-ce:
     # version: 4.3.5.0
     servers:
       - name: server1
         ip: 10.10.10.1
       - name: server2
         ip: 10.10.10.2
       - name: server3
         ip: 10.10.10.3
     global:
       # Please set devname as the network adaptor's name whose ip is  in the setting of severs.
       # if set severs as "127.0.0.1", please set devname as "lo"
       # if current ip is 192.168.1.10, and the ip's network adaptor's name is "eth0", please use "eth0"
       devname: eth0
       cluster_id: 1
       # please set memory limit to a suitable value which is matching resource.
       memory_limit: 8G # The maximum running memory for an observer
       system_memory: 2G # The reserved system memory. system_memory is reserved for general tenants. The default value is 30G.
       datafile_size: 20G # Size of the data file.
       datafile_next: 20G # the auto extend step. Please enter an capacity, such as 2G
       datafile_maxsize: 200G # the auto extend max size. Please enter an capacity, such as 20G
       log_disk_size: 20G # The size of disk space used by the clog files.
       cpu_count: 16
       scenario: htap
       enable_auto_start: true
       mysql_port: 2881 # External port for OceanBase Database. The default value is 2881. DO NOT change this value after the cluster is started.
       rpc_port: 2882 # Internal port for OceanBase Database. The default value is 2882. DO NOT change this value after the cluster is started.
       obshell_port: 2886 # Operation and maintenance port for Oceanbase Database. The default value is 2886. This parameter is valid only when the version of oceanbase-ce is 4.2.2.0 or later.
       production_mode: false
       # The working directory for OceanBase Database. OceanBase Database is started under this directory. This is a required field.
       home_path: /home/admin/observer
       # The directory for data storage. The default value is $home_path/store.
       data_dir: /data/observer
       # The directory for clog, ilog, and slog. The default value is the same as the data_dir value.
       redo_dir: /redo/observer
       ocp_agent_monitor_username: ocp_monitor
       ocp_agent_monitor_password: ****** # The password for obagent monitor user
       root_password: ****** # root user password, can be empty
       proxyro_password: ****** # proxyro user pasword, consistent with obproxy's observer_sys_password, can be empty
     server1:
       zone: zone1
     server2:
       zone: zone2
     server3:
       zone: zone3
   ```

The meanings of the configuration items in the configuration file can be found in the **Configuration Item Description** section of [Configuration File Description](../100.configuration-file-description.md). Please note the following:

   * If the password is not configured in the configuration file, obd will automatically generate a random password. After the deployment is successful, you can view the corresponding configuration item in the configuration file by using the `obd cluster edit-config` command to obtain the password.

   * If the OceanBase Database version to be deployed is not less than V4.2.5, and the `scenario` is not configured in the configuration file, obd will provide interactive options for you to select the load type.

   * If you set `enable_auto_start` to `true`, the observer process will start automatically when the system boots. This feature requires that the deployment user has sudo privileges and that the deployment environment is not a container environment.

4. Configure ODP

   <main id="notice" type='explain'>
     <h4>Note</h4>
     <p>obd supports deploying the Enterprise Edition of ODP. Here, we take the Community Edition of ODP as an example.</p>
   </main>

   ```yaml
   obproxy-ce:
     # version: 4.3.2.0
     depends:
       - oceanbase-ce
     servers:
       - 10.10.10.1
     global:
       listen_port: 2883 # External port. The default value is 2883.
       prometheus_listen_port: 2884 # The Prometheus port. The default value is 2884.
       rpc_listen_port: 2885
       enable_obproxy_rpc_service: true
       home_path: /home/admin/obproxy
       client_session_id_version: 2 # This parameter is used to specify whether to use the new logic to generate the client session ID. The parameter type is integer. The value range is [1, 2] and the default value is 2 (use the new logic).
       proxy_id: 5 # This parameter is used to set the ID for an ODP. The parameter type is integer. The default value is 0 and the value range is [0, 8191].
       enable_cluster_checkout: false
       skip_proxy_sys_private_check: true
       enable_strict_kernel_release: false
       obproxy_sys_password: ****** # obproxy sys user password, can be empty. When a depends exists, obd gets this value from the oceanbase-ce of the depends.
       observer_sys_password: ***** # proxyro user pasword, consistent with oceanbase-ce's proxyro_password, can be empty. When a depends exists, obd gets this value from the oceanbase-ce of the depends.
   ```

   The meanings of the configuration items in the configuration file can be found in the **Configuration Item Description** section of [Configuration File Description](../100.configuration-file-description.md), under the **ODP** section.

5. Configure monitoring components

   ```yaml
   obagent:
     depends:
       - oceanbase-ce
     servers:
       - name: server1
         ip: 10.10.10.1
       - name: server2
         ip: 10.10.10.2
       - name: server3
         ip: 10.10.10.3
     global:
       # The working directory for obagent. obagent is started under this directory. This is a required field.
       home_path: /home/admin/obagent
       # The port that pulls and manages the metrics. The default port number is 8088.
       monagent_http_port: 8088
       mgragent_http_port: 8089
       # Log path. The default value is log/monagent.log.
       log_path: log/monagent.log
       http_basic_auth_user: admin
       http_basic_auth_password: ******
   prometheus:
     servers:
       - 10.10.10.1
     depends:
       - obagent
     global:
       home_path: /home/admin/prometheus
       port: 9090 # The http port to use. Along with address, corresponds to the `web.listen-address` parameter.
       enable_lifecycle: true # Enable shutdown and reload via HTTP request. Corresponds to the `web.enable-lifecycle` parameter.
       data_dir: /home/admin/prometheus/data # Base path for metrics storage. Corresponds to the `storage.tsdb.path` parameter.
       basic_auth_users:  # Usernames and passwords that have full access to the web server via basic authentication. Corresponds to the `basic_auth_users` parameter.
         <username>: <password>  # The format of `basic_auth_users` : the key is the user name and the value is the password.
   alertmanager:
     servers:
       - 10.10.10.1
     depends:
       - prometheus
     global:
       home_path: /home/admin/alertmanager
       log_dir: /home/admin/alertmanager/log # Alertmanager log storage directory
       data_retention: 120h #Alertmanager how long to keep data form, corresponds to the `data.retention` parameter.
       port: 9093 # The http port to use. Along with address, corresponds to the `web.listen-address` parameter.
       data_dir: /home/admin/alertmanager/data # Base path for data storage. Corresponds to the `storage.path` parameter.
       basic_auth_users:  # Usernames and passwords that have full access to the web server via basic authentication. Corresponds to the `web.config.fil` parameter.
         <username>: <password>  # The format of `basic_auth_users` : the key is the user name and the value is the password.
       receivers: #one or more notification list
         - email
         - mock_webhook
     email:
       receiver_type: email
       to: "<to_email>"
       from: "<from_email>"
       smarthost: "smtp.xx.com:xxx"
       auth_username: "smtp_username"
       auth_password: "smtp_password"
       send_resolved: true
     mock_webhook:
       receiver_type: webhook
       url: http://<host>:<port>/
   ```

For details about the configuration items in the configuration file, see the **Configuration Item Description** section in [Configuration File Description](../100.configuration-file-description.md). This section describes the **OBAgent**, **Prometheus**, and **Alertmanager** configuration items.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>The following example shows how to configure the <code>email</code> and <code>webhook</code> notification types. You need to modify the configuration information based on your actual situation. For information about how to configure other notification types, see the <b>receivers</b> section in the <b>Alertmanager</b> section of <a href="../100.configuration-file-description.md">Configuration File Description</a>.</p>
</main>

### Step 2: Deploy OceanBase Database

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>For more information about the commands used in this section, see <a href="../../../300.obd-command/100.cluster-command-groups.md">Cluster commands</a>. </p>
</main>

1. Deploy an OceanBase cluster.

   ```shell
   [admin@test001 ~]$ obd cluster deploy obtest -c alertmanager.yaml
   ```

   In this example, the cluster name is `obtest`, and the configuration file is `alertmanager.yaml`. You can customize the cluster name and specify the required configuration file based on your actual situation.

   This command checks whether the directories pointed to by `home_path` and `data_dir` are empty. If the directories are not empty, an error is returned. If you confirm that all the content in the directories can be deleted, you can add the `-f` option to forcibly clear the directories.

2. Start the OceanBase cluster.

   ```shell
   [admin@test001 ~]$ obd cluster start obtest
   ```

### Step 3: Verify the deployment

After the deployment is complete, you can verify whether Alertmanager is working properly by following these steps:

1. Verify the Alertmanager web interface

   Copy the Alertmanager URL from the deployment output and access the Alertmanager web interface in a browser:

   ```shell
   http://10.10.10.1:9093
   ```

   In Alibaba Cloud or other cloud environments, the output may show an internal IP address instead of a public IP address. You need to use the correct address to access it. After accessing the interface, log in using the username and password configured in the `basic_auth_users` section.

2. Check the status of Alertmanager

   ```shell
   [admin@test001 ~]$ obd cluster display obtest
   ```

   The output should show the Alertmanager component status as `active`.
