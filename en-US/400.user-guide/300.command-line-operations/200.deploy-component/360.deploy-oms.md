# Deploy OMS

This topic describes how to deploy OceanBase Migration Service (OMS) by using an obd configuration file in a CentOS Linux 7.9 environment based on the x86 architecture.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>Currently, obd supports only OMS Community Edition V4.2.11 and later. </p>
</main>

## Prerequisites

Before you start, make sure that you meet the following requirements:

* You have installed obd V4.0.0 or later. We recommend that you install the latest version. For more information, see [Install obd](../../../200.quick-start/100.install-obd.md).

* The server where you want to deploy OMS meets the deployment requirements. For more information, see [Deploy OMS Community Edition](https://www.oceanbase.com/docs/community-oms-cn-1000000004253109) in the documentation of OceanBase Migration Service.

* Docker is installed on the server where you want to deploy OMS.

* If you want OMS to collect and display monitoring data, you must deploy and configure a time series database. At present, only InfluxDB V1.8 is supported. For more information, see [Deploy a time series database](https://www.oceanbase.com/docs/community-oms-cn-1000000004253199).

* If you plan to deploy OMS separately, you must prepare a database for storing the metadata of OMS Community Edition. The database can be MySQL or OceanBase Database. We recommend that you use OceanBase Database Community Edition.
  
  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>To improve system reliability, we recommend that you implement a high-availability database solution for MetaDB. This will effectively ensure the 7x24-hour stable operation of OMS core services and reduce the risk of business interruption. </p>
  </main>

* If you plan to deploy OceanBase Database as MetaDB, make sure that the OBServer node supports the AVX instruction set (this applies only to servers with the x86 architecture). You can run the `lscpu | grep Flags | grep avx` command to check whether the AVX instruction set is supported.
  
  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>When you use a server with the x86 architecture, if the version of OceanBase Database to be deployed is in the following ranges, there is no restriction on whether the server supports the AVX instruction set: </p>
    <ul>
    <li>For V4.2.x, the version must be V4.2.5.6 or later. </li>
    <li>For V4.3.x, the version must be V4.3.5.4 or later. </li>
    <li>For V4.4.x, the version must be V4.4.1.0 or later. </li>
    </ul>
  </main>

* In an offline deployment scenario, if you plan to deploy OceanBase Database as MetaDB and deploy it on a server with the ARM architecture, check whether the OBServer node supports the LSE instruction set. You can run the `lscpu | grep Flags | grep atomics` command to check whether the LSE instruction set is supported. If the server does not support the LSE instruction set, you must download the OceanBase Database installation package with the `nonlse` parameter and use the `obd mirror clone` command to upload the package to the local image repository of obd.
  
  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>The OceanBase Database installation package with the <code>nonlse</code> parameter is not included in the OceanBase All-in-One package. </p>
  </main>

* If you plan to deploy OceanBase Database as MetaDB, make sure that the required installation packages are available in the obd image repository. For example, the installation package of OceanBase Database.
  
  If the server where obd is installed can connect to the Internet, the required installation packages will be automatically downloaded from the remote image repository during deployment. If the server where obd is installed cannot connect to the Internet, you can download all installation packages from the [OceanBase Software Download Center](https://en.oceanbase.com/softwarecenter) and use the `obd mirror clone` command to upload the packages to the local image repository of obd. After the upload is complete, you can run the `obd mirror list local` command to view the installation packages in the local image repository.

## Considerations

The High Availability (HA) feature is disabled by default in OceanBase Migration Service Community Edition. After deployment, you can enable HA by accessing the OMS console and setting the `enable` parameter in the `ha.config` file to `true`. For more information, see [Modify the HA configuration](https://www.oceanbase.com/docs/community-oms-cn-10000000042531647) in the OceanBase Migration Service documentation.

tab Deploy OMS separately

### Step 1: Load the OMS Community Edition package

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>If you plan to deploy multiple nodes for OMS, each node must execute the following steps.</p>
</main>

1. Obtain the OMS installation package.

   For information on how to obtain the OMS community edition installation package, visit the [OceanBase Software Download Center](https://en.oceanbase.com/softwarecenter). The installation package is a `.tar.gz` file with the name starting with `oms`, such as `oms_4.2.11-ce.tar.gz`.

2. Load the OMS installation package to a local image repository of the Docker container.

   ```shell
   [admin@test ~]$ sudo docker load -i oms_4.2.11-ce.tar.gz
   ```

3. Verify whether the loading is successful.

   ```shell
   [admin@test ~]$ sudo docker images
   ```

   The output is as follows:

   ```shell
   REPOSITORY                                    TAG                 IMAGE ID       CREATED      SIZE
   reg.docker.alibaba-inc.com/oceanbase/oms-ce   feature_4.2.11_ce   26f5f1554fc5   2 days ago   12.5GB
   ```

### Step 2: Modify the configuration file

1. Create a configuration file.

   Run the following command to create a configuration file. The following example is named `oms-only-config.yaml`, which you can customize.

   ```shell
   [admin@test ~]$ vim oms-only-config.yaml
   ```

2. Modify user information.

   You can copy the following content and modify it to suit your specific scenario.

   ```yaml
   ## Only need to configure when remote login is required
   user:
     username: admin
   #   password: your password if need
     key_file: /home/admin/.ssh/id_rsa
   #   port: your ssh port, default 22
   #   timeout: ssh connection timeout (second), default 30
   ```

   `username` specifies the user name for logging in to the target device. Make sure that your user account has write permission to the user home directory. `password` and `key_file` are both used to authenticate the user. Typically, only one of them is required.

   <main id="notice" type='notice'>
      <h4>Note</h4>
      <p>After you specify the key path, if the key does not require a password, you can remove the <code>password</code> section to avoid using the key for authentication, which may cause an authentication failure.</p>
   </main>

3. Change OMS settings.

   You can copy and modify the following sample code as needed. For more information about the configuration parameters, see the **Parameter Description** section in [Configuration file description](../100.configuration-file-description.md).

   ```yaml
   oms:
     type: docker
     tag: feature_4.2.11_ce
     image_name: reg.docker.alibaba-inc.com/oceanbase/oms-ce
     servers:
       - name: server1
         ip: 10.10.10.1
       - name: server2
         ip: 10.10.10.2
       - name: server3
         ip: 10.10.10.3
     global:
       oms_meta_host: "10.10.10.1" # OMS meta database host address
       oms_meta_password: "******" # Password for OMS meta database user
       oms_meta_port: 2881 # Port number for OMS meta database connection
       oms_meta_user: root # Username for OMS meta database connection
       mount_path: /data/1/oms # Mount path for OMS data storage
       ghana_server_port: 8090 # Port for ghana server
       nginx_server_port: 8089 # Port for nginx server
       cm_server_port: 8088 # Port for cluster manager server
       # tsdb_enabled: "true"
       # tsdb_password: ""
       # tsdb_service: "INFLUXDB"
       # tsdb_url: "10.10.10.1:8086"
       # tsdb_username: "admin"
       regions:
         - cm_location: 1
           cm_is_default: true
           cm_region: hz
           cm_url: http://10.10.10.1:8088
           cm_nodes:
             - 10.10.10.1
             - 10.10.10.3
         - cm_location: 2
           cm_is_default: false
           cm_region: bj
           cm_url: http://10.10.10.2:8088
           cm_nodes:
             - 10.10.10.2
   ```

### Step 3: Deploy OMS

1. Deploy the OMS.

   ```shell
   [admin@test ~]$ obd cluster deploy oms -c oms-only-config.yaml
   ```

   The `oms` in the preceding command represents the name of the cluster. You can customize the name according to the actual situation. After a successful deployment, the CLI outputs the corresponding start-up command. The output is as follows:

   ```shell
   Open ssh connection ok
   +---------------------------------------------------------+
   |                         Packages                        |
   +------------+-------------------+---------+--------------+
   | Repository | Tag               | Release | Hash         |
   +------------+-------------------+---------+--------------+
   | oms        | feature_4.2.11_ce | -       | 26f5f1554fc5 |
   +------------+-------------------+---------+--------------+
   Repository integrity check ok
   Load param plugin ok
   Initializes OMS mount path ok
   Parameter check ok
   oms deployed
   Please execute ` obd cluster start oms ` to start
   Trace ID: 75241e2a-c133-11f0-910c-00163e1c4eb2
   If you want to view detailed obd logs, please run: obd display-trace 75241e2a-c133-11f0-910c-00163e1c4eb2
   ```

2. Start OMS.

   ```shell
   [admin@test ~]$ obd cluster start oms
   ```

   After the cluster is started, related information about the cluster is output. The output is as follows:

   ```shell
   Start oms ok
   OMS health check ok
   +-----------------------------------------------------------+
   |                            oms                            |
   +--------+-------------------+---------------+--------------+
   | region | url               | cm_is_default | nodes        |
   +--------+-------------------+---------------+--------------+
   | hz     | 10.10.10.1:8089   | True          | 10.10.10.1   |
   | bj     | 10.10.10.2:8089   | False         | 10.10.10.2   |
   +--------+-------------------+---------------+--------------+
   oms running
   Trace ID: 796b1a4c-c133-11f0-b9ac-00163e1c4eb2
   If you want to view detailed obd logs, please run: obd display-trace 796b1a4c-c133-11f0-b9ac-00163e1c4eb2
   ```

### Step 2: Modify the configuration file

1. Create the configuration file.

   Run the following command to create a configuration file named `oms-config.yaml` (you can change the name to your custom name).

   ```shell
   [admin@test ~]$ vim oms-config.yaml
   ```

2. Modify user information.

   You can copy the following content and modify it as needed based on your actual scenario. 1. Prepare a script that contains a test request to an API that is to be tested. For example, you can prepare the script by using Postman. 2. Save the script in a file, for example, testScript.py. 3. Configure a script file in the script file group and upload the script file. 4. Create a script task. 5. Configure the script task to run the script. 6. Execute the script task.

   ```yaml
   ## Only need to configure when remote login is required
   user:
     username: admin
   #   password: your password if need
     key_file: /home/admin/.ssh/id_rsa
   #   port: your ssh port, default 22
   #   timeout: ssh connection timeout (second), default 30
   ```

   `username` is the username of the user you want to log in with. Make sure the username has write permissions for the home directory. `password` and `key_file` are both used to verify the user. Normally, only one of them needs to be filled in.

   <main id="notice" type='notice'>
      <h4>Note</h4>
      <p>After you configure the secret key path, if your secret key does not contain a password, comment or delete <code>password</code> to prevent it from being recognized as the secret key password during login, which can result in authentication failure. </p>
   </main>
