# Cluster commands

obd has multiple levels of commands, and you can use the `-h/--help` option at each level to view the help information of subcommands. Similarly, when an error occurs during the execution of subcommands at each level, you can use the `-v/--verbose` option to view the detailed execution process of the command.

The smallest unit for cluster command operations in obd is a deployment configuration. A deployment configuration is a `yaml` file that contains all the configuration information for the entire deployment, including server login information, component information, component configuration information, and component server lists.

Before you use obd to start a cluster, you need to register the deployment configuration of the cluster in obd. You can use `obd cluster edit-config` to create an empty deployment configuration, or use `obd cluster deploy -c config` to import a deployment configuration.

## obd cluster autodeploy

You can use this command to specify a simple configuration file. obd generates a complete configuration with the maximum specifications based on the resources of the target machines and deploys and starts the cluster.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>After you modify the configuration file, use this command to deploy the cluster. obd generates a configuration based on the resources of the machines and overwrites the modified configuration items. Therefore, this command can be used only to deploy the cluster based on the specifications of the configuration generated by obd. </p>
</main>

```shell
obd cluster autodeploy <deploy name> -c <yaml path> [-f] [-U] [-A] [-s]

# example
obd cluster autodeploy test -c all-components.yaml
```

The `deploy name` parameter specifies the name of the deployment, which can be considered an alias for the configuration file.


The `deploy name` parameter specifies the name of the deployment, which can be considered an alias for the configuration file.

## obd cluster deploy

You can run this command to deploy a cluster based on the configuration.

This command finds suitable images based on the information of the components in the deployment configuration file and installs them to the local repository. This process is called local installation. Then, it distributes the components of the appropriate version in the local repository to the target servers. This process is called remote installation.

During local installation and remote installation, the server dependencies required for the components are checked. You can directly deploy a component registered in obd by specifying the `deploy name`, or you can pass the `yaml` configuration information.

```shell
obd cluster deploy <deploy name> [-c <yaml path>] [-f] [-U] [-A]

# example
obd cluster deploy test -c all-components-min.yaml
```

The `deploy name` parameter specifies the name of the deployment, which can be considered an alias for the configuration file.

The following table describes the options.

|              Option              | Required |  Data type  |  Default value  |                                                                           Description                                                                            |
|-------------------------------|------|--------|-------|---------------------------------------------------------------------------------------------------------------------------------------------------------|
| -c/--config                   | No   | string | N/A   | Specifies the path of the required YAML file. obd deploys the cluster based on the specified YAML file and registers the deployment configuration to obd. If the `deploy name` parameter is specified, the configuration is overwritten. </br>If you do not specify this option, obd finds the registered configuration information based on the `deploy name` parameter.                                                  |
| -f/--force                    | No   | bool   | false | This option does not require a value. The configuration in the command takes effect. When you specify this option, obd forcibly clears the working directory. ## obd cluster start

Starts a deployed cluster and prints the cluster status.

```shell
obd cluster start <deploy name> [flags]

# example
obd cluster start test -S
```

The `deploy name` parameter specifies the name of the deployment, which can be considered an alias for the configuration file.

The following table describes the options.

|            Option            | Required |  Data type  |  Default value  |                                                 Description                                                  |
|---------------------------|------|--------|-------|-----------------------------------------------------------------------------------------------------|
| -s/--servers              | No   | string | Empty  | The list of servers. The value of the `name` parameter in the `servers` section of the YAML file is specified. If the `name` parameter is not specified, the `ip` value is used. The values are separated with commas (,). This option specifies the servers to be started. If not all servers of the component are started, the bootstrap process is not executed. |
| -c/--components           | No   | string | Empty  | The list of components. The values are separated with commas (,). This option specifies the components to be started. If not all components of the configuration are started, the configuration will not be in the running state.                                          |
| --wop/--without-parameter | No   | bool   | false | Starts the cluster without parameters. When you specify this option, obd starts the deployed cluster without parameters. This option is not effective for the first start of a node.                                                                    |
| -S/--strict-check         | No   | bool   | false | Some components are checked before they are started. If the check fails, obd issues a warning but does not forcibly stop the process. </br>When you specify this option, the process exits immediately after the check fails. We recommend that you specify this option to avoid startup failures caused by insufficient resources.                |

## obd cluster list

Displays the status of all clusters (deploy names) registered in the current obd.

```shell
obd cluster list
```

The status of a cluster registered in obd can be one of the following:

* configured: The cluster is configured. This indicates that the cluster's configuration file is included in obd, but the cluster is not yet deployed. You can execute the `obd cluster deploy` command to deploy the cluster.

* deployed: The cluster is deployed. This indicates that the cluster is deployed but not yet started. You can execute the `obd cluster start` command to start the cluster.

* running: The cluster is running.

* stopped: The cluster is stopped. This indicates that some components in the cluster are stopped. You can execute the `obd cluster start` command to start the cluster.

* upgrading: The cluster is being upgraded. This indicates that some components in the cluster are being upgraded.

* destroyed: The cluster is destroyed.

## obd cluster display

Displays the status of the specified cluster.

```shell
obd cluster display <deploy name>

# example
obd cluster display test
```

The `deploy name` parameter specifies the deployment name, which can be considered an alias for the configuration file. Starting from V3.2.0, if an encryption key is set in obd, the cluster information output by the display command will be in an encrypted state. If you want to output the plaintext password, you can add the `--epk`/`--encryption-passkey` option to specify the key for verification.

## obd cluster reload

Reloads a running cluster. After you modify the configuration information of a running cluster using `edit-config`, you can execute the `reload` command to apply the modifications.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>Not all configuration items can be applied using <code>reload</code>. Some configuration items require a cluster restart or even a re-deployment to take effect. Please operate based on the information returned after <code>edit-config</code>. </p>
</main>

```shell
obd cluster reload <deploy name>

# example
obd cluster reload test
```

The `deploy name` parameter specifies the deployment name, which can be considered an alias for the configuration file.

## obd cluster restart

Restarts a running cluster. By default, the restart is parameter-free. After you modify the configuration information of a running cluster using `edit-config`, you can execute the `obd cluster restart <deploy name> --wp` command to apply the modifications.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>Not all configuration items can be applied using <code>restart</code>. Some configuration items require a cluster re-deployment to take effect. Please operate based on the information returned after <code>edit-config</code>. </p>
</main>

```shell
obd cluster restart <deploy name>

# example
obd cluster restart test -c obproxy-ce --wp
```

The `deploy name` parameter specifies the deployment name, which can be considered an alias for the configuration file.

The following table describes the options.

|          Option          | Required |  Data Type  |  Default Value  |                             Description                             |
|-----------------------|------|--------|-------|------------------------------------------------------------|
| -s/--servers          | No    | string | Empty     | The list of servers. The value of `name` in the `servers` section of the `yaml` file is specified. If the `name` value is not configured, the `ip` value is used. Separate the values with commas (,). This option specifies the servers to restart.                                             |
| -c/--components       | No    | string | Empty     | The list of components. Separate the values with commas (,). This option specifies the components to restart. If not all components are started, the cluster will not be in the running state. |
| --wp/--with-parameter | No    | bool   | false | Parameter-based restart. This option ensures that the configuration items that take effect after the restart are effective.                                        |

## obd cluster redeploy

Redeploys a running cluster. After you modify the configuration information of a running cluster using `edit-config`, you can execute the `redeploy` command to apply the modifications.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>This command will destroy and re-deploy the cluster. Data in your cluster will be lost. Please back up your data before proceeding. </p>
</main>

```shell
obd cluster redeploy <deploy name> [-f]

# example
obd cluster redeploy test -f
```

The `deploy name` parameter specifies the deployment name, which can be considered an alias for the configuration file.

|       Option       | Required |  Data Type  | Default Value |                              Description                               |
|-----------------|------|--------|-----|---------------------------------------------------------------|
| -f/--force-kill    | No    | bool | false   | Before obd executes the destroy command, it checks whether any processes are running. These running processes may be left over from a failed `start` operation or may belong to another cluster due to overlapping configurations. Regardless of the cause, if any processes are still running in the working directory, obd will stop executing the `obd cluster redeploy` command. When you enable the `-f` option, obd will forcibly stop any running processes and proceed with the `obd cluster redeploy` command. |
| --confirm | No  | bool   | false    | This option requires you to confirm whether to restart the cluster during the execution of the command. If you enable this option, the confirmation step will be skipped, and the cluster will be restarted directly.  |
| --igs/--ignore-standby | No    | string | Empty   | If a standby tenant exists in another cluster for a tenant in the current cluster, obd will forcibly execute the `obd cluster redeploy` command. After the cluster is destroyed, the standby tenant will no longer be usable.    |

## obd cluster prune-config

Deletes the configuration files of a destroyed or configured cluster. When a cluster is in the `destroyed` or `configured` state (you can view the cluster status using the `obd cluster list` command), this command can be used to completely delete the specified cluster's configuration files to free up storage space.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <ul>
  <li><p>This command can only delete the configuration files of a cluster in the <code>destroyed</code> or <code>configured</code> state. If the cluster is not in either of these states, the command will return an error and exit.</p></li>
  <li><p>After deleting the configuration file, you cannot deploy the cluster based on the current configuration again. That is, when you execute the deployment command, you must specify the configuration file path again. This operation is irreversible.</p></li>
  </ul>
</main>

```shell
obd cluster prune-config <deploy name> [--confirm]

# example
obd cluster prune-config test
obd cluster prune-config test --confirm
```

The `deploy name` parameter specifies the name of the deployed cluster, which can be considered an alias for the configuration file. The `--confirm` option is used to control whether to skip the confirmation prompt during command execution. This option does not require a value; specifying it indicates that the confirmation prompt should be skipped, and the configuration file will be directly deleted.

<main id="notice" type='explain'>
