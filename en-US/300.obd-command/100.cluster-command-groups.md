# Cluster commands

obd has multiple levels of commands. You can use the `-h/--help` option at each level to view the help information of the subcommands. Similarly, when an error occurs during the execution of subcommands at each level, you can use the `-v/--verbose` option to view the detailed execution process of the commands.

The smallest unit for cluster command operations in obd is a deployment configuration. A deployment configuration is a `yaml` file that contains all the configuration information for the entire deployment, including server login information, component information, component configuration information, and component server lists.

Before you use obd to start a cluster, you need to register the deployment configuration of the cluster with obd. You can use the `obd cluster edit-config` command to create an empty deployment configuration, or use the `obd cluster deploy -c config` command to import a deployment configuration.

## obd cluster autodeploy

You can specify a simple configuration file to use the obd cluster autodeploy command. The obd cluster autodeploy command generates a complete configuration file with the maximum specifications based on the resources of the target machine and deploys and starts the cluster.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>After you modify the configuration file, you can use the obd cluster autodeploy command to deploy the cluster. The obd cluster autodeploy command generates a configuration file based on the resources of the target machine and overwrites the modified configuration file. Therefore, you can use the obd cluster autodeploy command to deploy the cluster only when the obd cluster autodeploy command generates a configuration file. </p>
</main>

```shell
obd cluster autodeploy <deploy name> -c <yaml path> [-f] [-U] [-A] [-s]

# example
obd cluster autodeploy test -c all-components.yaml
```

## obd cluster deploy

You can run this command to deploy a cluster based on the configuration.

This command finds suitable images based on the component information in the deployment configuration file and installs them to the local repository. This process is called local installation. Then, it distributes the components of the appropriate version in the local repository to the target servers. This process is called remote installation.

In both local and remote installation, the server dependencies required for the components are checked. You can directly deploy the `deploy name` registered in obd or pass in the `yaml` configuration information.

```shell
obd cluster deploy <deploy name> [-c <yaml path>] [-f] [-U] [-A]

# example
obd cluster deploy test -c all-components-min.yaml
```

The `deploy name` parameter specifies the deployment name, which can be considered an alias for the configuration file.

Starts a deployed cluster and prints the cluster status.

```shell
obd cluster start <deploy name> [flags]

# example

```

The `deploy name` parameter specifies the deployment name, which can be considered an alias for the configuration file.

The following table describes the options.

|---------------------------|------|--------|-------|-----------------------------------------------------------------------------------------------------|

If the `name` value is not specified in `servers`, the `ip` value is used instead. The servers are separated by commas (,). This option specifies the servers to start. If not all servers under a component are started, the start command will not execute the bootstrap process. |
| -c/--components           | No    | string | Empty  | The list of components, separated by commas (,). This option specifies the components to start. If not all components are started, the configuration will not be in the running state.                                          |

## obd cluster list

Displays the status of all clusters (deploy name) registered in the current obd.

```shell
obd cluster list
```

The status of a cluster registered in obd can be one of the following:

* configured: The cluster has been configured. This indicates that the cluster configuration file has been included in obd, but the cluster has not been deployed. You can execute the `obd cluster deploy` command to deploy the cluster.

* deployed: The cluster has been deployed. This indicates that the cluster has been deployed, but it has not been started. You can execute the `obd cluster start` command to start the cluster.

* running: The cluster is running.

* stopped: The cluster has been stopped. This indicates that some components in the cluster have been stopped. You can execute the `obd cluster start` command to start the cluster.

* upgrading: The cluster is being upgraded. This indicates that some components in the cluster are being upgraded.

* destroyed: The cluster has been destroyed.

Displays the status of a specified cluster.

```shell
# example

```

## obd cluster reload

Reloads a running cluster. After you modify the configuration information of a running cluster using `edit-config`, you can execute the `reload` command to apply the modifications.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>Not all configuration items can be applied by using the <code>reload</code> command. Some configuration items require a cluster restart or even a re-deployment to take effect. Please operate based on the information returned after executing <code>edit-config</code>. </p>
</main>

```shell
obd cluster reload <deploy name>

# example
obd cluster reload test
```

The `deploy name` parameter specifies the deployment name, which can be considered an alias for the configuration file.

## obd cluster restart

Restarts a running cluster. By default, the restart is parameter-free. After you modify the configuration information of a running cluster using `edit-config`, you can execute the `obd cluster restart <deploy name> --wp` command to apply the modifications.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>Not all configuration items can be applied by using the <code>restart</code> command. Some configuration items require a cluster re-deployment to take effect. Please operate based on the information returned after executing <code>edit-config</code>. </p>
</main>

```shell
obd cluster restart <deploy name>

# example
obd cluster restart test -c obproxy-ce --wp
```

The `deploy name` parameter specifies the deployment name, which can be considered an alias for the configuration file.

The following table describes the options.

|          Option          | Required |  Data Type  |  Default Value  |                             Description                             |
|-----------------------|------|--------|-------|------------------------------------------------------------|
| -s/--servers          | No    | string | Empty string     | The list of servers, followed by the `name` value in the `yaml` file. If the `servers` section does not specify the `name` value, the `ip` value is used. The servers are separated by commas. This option specifies the servers to be restarted.                                             |
| -c/--components       | No    | string | Empty string     | The list of components, separated by commas. This option specifies the components to be restarted. If not all components are started, the cluster does not enter the running state. |
| --wp/--with-parameter | No    | bool   | false | Parameter-based restart. This option specifies the configuration items to be applied.                                        |

## obd cluster redeploy

Redeploys a running cluster. After you modify the configuration information of a running cluster using `edit-config`, you can execute the `redeploy` command to apply the modifications.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>This command will destroy the cluster and redeploy it. Your cluster data will be lost. Please back up your data before proceeding. </p>
</main>

```shell
obd cluster redeploy <deploy name> [-f]

# example
obd cluster redeploy test -f
```

The `deploy name` parameter specifies the deployment name, which can be considered an alias for the configuration file.

|       Option       | Required |  Data Type  | Default Value |                              Description                               |
|-----------------|------|--------|-----|---------------------------------------------------------------|
| -f/--force-kill    | No    | bool | false   | Before obd executes the destroy command, it checks whether any processes are running. These processes may be left over from a failed `start` operation or may belong to another cluster due to overlapping configurations. Regardless of the cause, if any processes are still running in the working directory, obd will stop executing the `obd cluster redeploy` command. When you enable the `-f` option, obd will forcibly stop any running processes and proceed with the `obd cluster redeploy` command. |
| --confirm | No  | bool   | false    | This option specifies whether to confirm the restart of the cluster during the execution of the command. If you enable this option, obd will skip the confirmation process and directly restart the cluster.  |
| --igs/--ignore-standby | No    | string | Empty string   | If a standby tenant exists in another cluster for a tenant in the current cluster, obd will forcibly execute the `obd cluster redeploy` command. After the cluster is destroyed, the standby tenant will no longer be usable.    |

## obd cluster prune-config

Deletes the configuration files of a destroyed or configured cluster. When a cluster is in the `destroyed` or `configured` state (you can view the cluster status using the `obd cluster list` command), this command can be used to completely delete the configuration files of the specified cluster to free up storage space.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <ul>
  <li><p>This command can only delete configuration files of clusters in the <code>destroyed</code> or <code>configured</code> state. If the cluster is not in one of these states, the command will return an error and exit.</p></li>
  <li><p>After the configuration file is deleted, the cluster cannot be redeployed based on the current configuration. That is, when executing the deployment command, you must specify the path to the configuration file again. This operation is irreversible.</p></li>
  </ul>
</main>

```shell
obd cluster prune-config <deploy name> [--confirm]

# example
obd cluster prune-config test
obd cluster prune-config test --confirm
```

The `deploy name` parameter specifies the name of the deployed cluster, which can be considered an alias for the configuration file. The `--confirm` option is used to control whether to skip the confirmation prompt during command execution. This option does not require a value. If specified, it skips the confirmation prompt and directly deletes the configuration file.

## obd cluster tenant restore

You can run this command to restore backup data to a specified tenant. Currently, only tenant-level restore is supported.

```shell
obd cluster tenant restore <deploy name> <tenant name> <data backup uri> <archive log uri> [options]

#example
obd cluster tenant restore test obmysql 'file:///data/nfs/backup/data' 'file:///data/nfs/backup/log' -z zone1
```

The following table describes the required parameters of the command:

* `deploy name` specifies the deployment name, which can be considered an alias for the configuration file.

* `tenant name` specifies the tenant name. Make sure that no tenant with the same name exists. obd creates the tenant based on the settings.

* `data backup uri` specifies the directory path of the original data backup file.

* `archive log uri` specifies the directory path of the original log archive file.

The following table describes the options.

|          Option           | Required | Data Type | Default Value |                                                                        Description                                                                         |
| ------------------------- | -------- | -------- | ------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| -z/--zone    | No  | string   |  N/A  |  The name of the zone to which the tenant to be restored belongs. If multiple zones are specified, separate them with commas (`,`). If this option is not specified, all zones are used by default.   |
| --unit-num                | No   | int    |  1     | The number of units for the tenant in a zone.                                                                   |
| --replica-type            | No   | string | FULL  | The replica type of the tenant in a zone. Valid values: <ul><li><code>FULL</code>: full-featured replica</li><li><code>READONLY</code>: read-only replica</li></ul> |
| -p/--primary-zone         | No   | string   | random | The primary zone of the tenant to be restored.                                               |
| -T/--timestamp            | No   | time.time  |  N/A      | The timestamp to which the data is to be restored. If this option is specified, the data is restored up to and including the specified timestamp.                |
| -S/--scn                  | No   | int      |  0     | The SCN to which the data is to be restored. If this option is specified, the data is restored up to and including the specified SCN.                      |
| -s/--ha-high-thread-score | No   | int      | 10     | The number of high-priority threads for high availability. Valid value: [0, 100].                    |
| -c/--concurrency          | No   | int      |  `${max-cpu}`      | The concurrency level for data restore. If this option is not specified, the default value is the MAX_CPU value of the tenant.              |
| -D/--decryption           | No   | []string  |  N/A      | The password of the backup set. If multiple passwords are set, all passwords must be specified and separated by commas (`,`).                                |
| -k/--kms-encrypt-info     | No   | string | N/A      | Key management information. If the data is not encrypted or the original key management service can be accessed during restore, you can omit this option.              |
| --memory-size    | No  |  string   | N/A  | The available memory of the tenant to be restored. We recommend that you set this parameter to the same value as that of the source tenant. If this parameter is not specified, the system automatically creates the tenant to be restored based on the remaining available resources of the cluster.  |
| --max-cpu        | No  | string    |  N/A  | The maximum available CPU of the tenant to be restored. The minimum value is 1. We recommend that you set this parameter to the same value as that of the source tenant. If this parameter is not specified, the system automatically creates the tenant to be restored based on the remaining available resources of the cluster.  |
| --min-cpu         |  No   | int   | N/A   | The minimum available CPU of the tenant. The minimum value is `1`. If this parameter is not specified, the default value is the same as `--max-cpu`.                                   |
| --max-iops        |  No   | int   | N/A   | The upper limit of IOPS of the tenant. The minimum value is 1024. The specified value must satisfy `--max-iops` >= `--min-iops`. If this parameter is not specified, the system automatically calculates the value of `--max-iops` based on the following rules:<ul><li>If <code>--min-iops</code> is specified, <code>--max-iops</code> is set to the value of <code>--min-iops</code>.</li><li>If <code>--min-iops</code> is not specified, both <code>--max-iops</code> and <code>--min-iops</code> are set to <code>INT64_MAX</code>.</li></ul>                            |
| --min-iops        |  No   | int   | N/A   | The lower limit of IOPS of the tenant. The minimum value is 1024. If this parameter is not specified, the system automatically calculates the value of `--min-iops` based on the following rules:<ul><li>If <code>--max-iops</code> is specified, <code>--min-iops</code> is set to the value of <code>--max-iops</code>.</li><li>If <code>--max-iops</code> is not specified, both <code>--min-iops</code> and <code>--max-iops</code> are set to <code>INT64_MAX</code>.</li></ul>                    |
| --log-disk-size   |  No   | int   | N/A   | The size of the unit log disk of the tenant. If this parameter is not specified, the default value is three times the memory specification. The minimum value is `2G`           |
