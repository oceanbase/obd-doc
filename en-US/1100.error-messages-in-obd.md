# Error codes

This topic summarizes the error codes that may occur during the obd process, including the following aspects.

## General error

### OBD-1000: Configuration conflict x.x.x.x: xxx port is used for x.x.x.x

Cause: The port is already used in the configuration file.

Solution: The following two solutions are available, depending on the deployment method.

- When you deploy by using the CLI, run the `obd cluster edit-config <deploy name>` command to open the configuration file, check the port configuration, and modify it. Then, run the command displayed in the CLI to make the modification take effect.

- When you deploy by using the GUI, click **<UI-TERM key="ocp-v2.Component.AddSamplingInspectStrategy.PreviousStep">Previous</UI-TERM>** to go to the **Cluster Configuration** (when you deploy OceanBase Database) or **<UI-TERM key="ocp-v2.Binlog.New.MetadbConfiguration">MetaDB Configuration</UI-TERM>** (when you deploy OCP) page, and find the port in the error message and modify it.

### OBD-1001: x.x.x.x:xxx port is already used

Cause: The port is already occupied.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>For more information about the port configuration items and default port numbers of each component, see <a href='https://ask.oceanbase.com/t/topic/35603118'>[SOP Series 20] Default port numbers of OceanBase Database server processes and ecosystem components</a>.</p>
</main>

Solution: You can end the process of the port or change the port to an unoccupied one. You can choose any of the following methods based on your needs.

- Method 1: If you deploy by using a configuration file, run the `obd cluster edit-config <deploy name>` command to open the configuration file and modify the port configuration in the file. Then, run the command displayed in the CLI to make the modification take effect.

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>For more information about the commands mentioned in Method 1, see <a href='300.obd-command/100.cluster-command-groups.md'>Cluster commands</a>.</p>
  </main>

- Method 2: If you deploy by using the `obd demo` command, run the following command to specify the port. The following example specifies the mysql_port of the oceanbase-ce component.

  ```shell
  obd demo --oceanbase-ce.mysql_port=3881
  ```

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>For more information about the commands mentioned in Method 2, see <a href='300.obd-command/000.obd-demo.md'>Quick deployment commands</a>.</p>
  </main>

- Method 3: If you deploy by using the GUI, click **Previous** until you find the port in the error message and change it to an unoccupied one.

### OBD-1002: Fail to init x.x.x.x path

Cause: The following two reasons may cause this error. You can determine the cause based on the specific error message.

1. The user specified in the configuration file (the current user by default if no user is specified) does not have write permissions for the corresponding directory.

2. The specified directory is not empty.

Solution:

For reason 1, you can use the following two methods to resolve the issue.

- Run the `obd cluster edit-config <deploy name>` command to open the configuration file, add or modify the user information in the file, and then run the command displayed in the CLI to make the modification take effect.

- Log in to the target server and grant write permissions for the corresponding directory to the current account.

For reason 2, you can use the following two methods to resolve the issue.

- Run the `obd cluster edit-config <deploy name>` command to open the configuration file, and change the value of the corresponding configuration item to an empty directory.

- If you confirm that the directory can be cleared, you can run the command again and add the `-f` option. In this case, obd will clear the directory using the current user.

### OBD-1003: fail to clean x.x.x.x:xxx

Cause: The user specified in the configuration file (the current user by default if no user is specified) does not have write permissions for the home_path.

Solution: You can use the following two methods to resolve the issue.

- Run the `obd cluster edit-config <deploy name>` command to open the configuration file, add or modify the user information in the file, and then run the command displayed in the CLI to make the modification take effect.

- Log in to the target server and grant write permissions for the corresponding directory to the current account.

### OBD-1004: Configuration conflict x.x.x.x: xxx is used for x.x.x.x

Cause: The configuration file contains a path conflict.

Solution: Check the configuration and modify it.

### OBD-1005: Some of the servers in the cluster have been stopped

Cause: All servers in the cluster must be online for subsequent operations. However, some servers in the current configuration have been stopped.

Solution: You can run the `obd cluster start <deploy_name> --wop` command to start all services.

### OBD-1006: Failed to connect to xxx

Cause:

1. The network between obd and the target server is disconnected.

2. The corresponding component process has exited or is not providing services.

3. The username and password do not match.

Solution:

For reason 1, fix the network connection.

For reason 2, try to start the component again. If the start fails, troubleshoot the error, such as **OBD-2002**.

For reason 3, the most common cause is that the user directly executed an SQL statement to change the password, resulting in a mismatch between the stored password in the configuration file and the actual password. In this case, you can use the following two methods to resolve the issue.

1. Execute an SQL statement to change the password back to the one stored by obd.

2. Execute the `vi ~/.obd/cluster/<deploy name>/config.yaml` command to modify the corresponding password in the configuration file to match the actual password of the component.

### OBD-1007: (x.x.x.x) The value of the ulimit parameter xxx must not be less than xxx (Current value: xxx)

Cause: The ulimit configuration does not meet the requirements.

Solution: You can modify the corresponding file in the `/etc/security/limits.d/` directory and the `/etc/security/limits.conf` file to meet the requirements.

### OBD-1008: (x.x.x.x) failed to get fs.aio-max-nr and fs.aio-nr

Cause: obd cannot obtain the aio configuration of the server.

Solution: Check whether the current user has the permission to view fs.aio-max-nr/fs.aio-nr.

```bash
cat /proc/sys/fs/aio-max-nr /proc/sys/fs/aio-nr
```

### OBD-1009: x.x.x.x xxx need config: xxx

Cause: The corresponding configuration is missing for the service-related component.

Solution: Run the `obd cluster edit-config <deploy name>` command to open the configuration file, and add the configuration item indicated in the error message to the file. Then, run the command displayed in the CLI to make the modification take effect.

### OBD-1010: x.x.x.x No such net interface: xxx

The error occurs because obd cannot obtain the devname.

To resolve this error, perform the following operations based on the deployment method.

- In command-line mode, run the `obd cluster edit-config <deploy_name>` command to open the configuration file. Add or modify the `devname` parameter in the configuration file. Then, run the command displayed in the command-line interface to make the modification take effect.

- In graphical interface mode, click **<UI-TERM key="ocp-v2.component.StepsMoveOutCluster.Step2.PreviousStep">Previous</UI-TERM>**. On the **Cluster Configuration** page (when you deploy OceanBase Database) or the **<UI-TERM key="ocp-v2.Binlog.New.MetadbConfiguration">MetaDB Configuration</UI-TERM>** page (when you deploy OCP), click **<UI-TERM key="ocp-v2.src.component.AddUnitSpecModal.MoreConfigurations">More Settings</UI-TERM>** in the **Cluster Configuration** section and set the devname.

### OBD-1011: (x.x.x.x) Insufficient AIO remaining (Avail: xxx, Need: xxx), The recommended value of fs.aio-max-nr is 1048576

The error occurs because the number of available AIOs is less than the number of AIOs required by the database.

To resolve this error, run the following command to modify the aio-max-nr parameter of Linux.

```bash
sudo sysctl fs.aio-max-nr=1048576
```

### OBD-1012: xxx

The error occurs for the following reasons:

1. A type conversion error occurs, for example, an int-type parameter is passed as a string.

2. The value of a parameter exceeds the specified range. For example, the value of `rpc_port` must be in the range of 1025 to 65535. If the value of `rpc_port` is not in the range, an error is returned.

3. A critical parameter is missing. For example, the `home_path` parameter is not configured.

To resolve this error, perform the following operations based on the cause.

- For case 1, check the parameter type and modify it.

- For case 2, check the parameter value and modify it.

- For case 3, check the parameter configuration. If a parameter is missing, configure the corresponding parameter.

### OBD-1013: xxx@x.x.x.x connect failed: xxx

The error occurs for the following reasons:

1. The username or password is incorrect.

2. The connection times out.

To resolve this error, if the error message contains the following content, run the `obd env set OBD_DISABLE_RSA_ALGORITHMS 1` command to disable the `rsa-sha2-512` and `rsa-sha2-256` algorithms.

```shell
Open ssh connection \Exception (client): Unable to agree on a pubkey algorithm for signing a 'ssh-rsa' key!
```

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>If you deploy the cluster in graphical interface mode, you must click <b>Exit</b> first. Then, run the <code>obd env set</code> command on the command-line interface and re-deploy the cluster in graphical interface mode. </p>
</main>

If the error message does not contain the preceding content, you can manually connect to the corresponding server by using the SSH command and verify whether the connection information is correct.

- If the connection fails, verify whether the connection information is correct and the server configurations are correct.

- If the connection is successful, modify the connection information based on the deployment method. The following two methods are available.

  - In command-line mode, run the `obd cluster edit-config <deploy_name>` command to open the configuration file. Add or modify the `user` parameter in the configuration file. Then, run the command displayed in the command-line interface to make the modification take effect.

  - In graphical interface mode, click **<UI-TERM key="ocp-v2.Cluster.Import.PreviousStep">Previous</UI-TERM>**. On the **Node Configuration** page (when you deploy OceanBase Database) or the **<UI-TERM key="ocp-v2.Binlog.New.MetadbConfiguration">MetaDB Configuration</UI-TERM>** page (when you deploy OCP), modify the **Deployment User Configuration** section.

If the cluster still cannot be deployed after the preceding troubleshooting, you can post a question in the [Q&A section](https://ask.oceanbase.com/) on the official website. A professional engineer will provide an answer.

### OBD-1015: Unable to confirm the primary-standby relationship, rerun with "--ignore-standby" option if you want to proceed despite the risks

The error occurs because the primary-standby relationship cannot be confirmed during the execution of the command.

To resolve this error, check whether a standby tenant exists in the current cluster or tenant. The following two methods are available based on whether the cluster is available.

- If the cluster is available, run the following command to check whether a standby tenant exists. Here is an example where the cluster name is test.

  ```shell
  obd cluster tenant show test -g
  ```

- If the cluster is unavailable, run the following command to check the primary-standby relationships of the current cluster or tenant. Here is an example where the cluster name is test.

  ```shell
  cat ~/.obd/cluster/test/inner_config.yaml
  ```

  Based on the output, run the following command on the corresponding cluster to check whether the primary-standby relationship still exists. Here is an example where the cluster name is test-standby.

  ```shell
  obd cluster tenant show test-standby -g
  ```

Based on the detection results and the current operation, the following solutions are available. For more information about the commands, see the corresponding command description in [Cluster commands](./300.obd-command/100.cluster-command-groups.md).

- If the current operation is an upgrade operation and a standby tenant exists in the current cluster or tenant, the version of the standby tenant must be no less than that of the primary tenant. Therefore, you can first upgrade the standby tenant and then upgrade the primary tenant. If both a primary tenant and a standby tenant exist in the current cluster, you can first run the `obd cluster tenant switchover` command to switch the primary tenant to the standby tenant. After the primary and standby tenants are upgraded, run the `obd cluster tenant switchover` command again to switch back.

  <main id="notice" type='explain'>
     <h4>Note</h4>
     <p>If the current cluster is upgraded to the same version, you can directly re-execute the command and add the <code>--ignore-standby</code> option to skip the check. </p>
   </main>

- If the current operation is not an upgrade operation (destroy/redeploy/drop) and a standby tenant exists in the current cluster or tenant, you can use the following solutions to remove the primary-standby relationship.

  - Run the `obd cluster tenant decouple` command on the standby tenant. The standby tenant will be upgraded to the primary tenant.

  - Run the `obd cluster stop` command on the cluster where the primary tenant is located to stop the cluster, and then run the `obd cluster tenant failover` command on the standby tenant. The standby tenant will be upgraded to the primary tenant.

  - Run the `obd cluster tenant drop` command on the standby tenant. The standby tenant will be deleted.

- If no standby tenant exists in the current cluster or tenant, or you can accept the risk of the standby tenant being unavailable, you can re-execute the command and add the `--ignore-standby` option to skip the check.

### OBD-1016: (xx.xx.xx.xx) failed to get xxx using command "sysctl -a"

The error occurs because the connection is abnormal or the operating system does not support the `sysctl -a` command.

To resolve this issue, you can retry the operation or ask a professional on the [Q&A page](https://ask.oceanbase.com/).

### OBD-1017: (xx.xx.xx.xx) The value of the "xxx" must be xxx

The error occurs because the kernel parameters of the operating system are not within the recommended range.

To ensure the stability of OceanBase Database in a production environment, obd checks the system environment and kernel parameters before starting OceanBase Database. This check ensures that the system configuration meets the recommended parameter settings of OceanBase Database. If the `production_mode` parameter is set to `true` or the `--strict-check` option is specified when you execute a command, the instance will be identified as a production environment. In this case, an error report will be triggered, and the startup will be terminated. Otherwise, only an alert will be issued, and the startup will not be terminated.

To resolve this issue, you can use the following methods based on your environment:

- If your environment is a production environment, you can use the `sysctl -w {kernel parameter name}="recommended value"` command or the `echo "kernel parameter name=recommended value" >> /etc/sysctl.conf; sysctl -p` command to modify the parameter configuration to meet the requirements.

- If your environment is a test environment and you do not have permission to modify the kernel parameters, you can use the `obd cluster edit-config {deployname}` command to modify the configuration file and set the `production_mode` parameter to `false` to skip the system parameter check.

### OBD-1018: could not change xxx

The error occurs because the configuration file specified by the command contains a configuration item that cannot be modified.

To resolve this issue, check whether the `user`, `depends`, `unuse_lib_repository`, or `auto_create_tenant` configuration item exists in the specified configuration file.

### OBD-1019: component xxx already in cluster

The error occurs because the component to be added already exists in the cluster. obd does not support adding an existing component to the cluster.

To resolve this issue, you can execute the `obd cluster edit-config` command to open the configuration file and check the component information in the cluster to confirm whether the component to be added already exists.

### OBD-1020: Update config for component xxx failed

The error occurs because the update of the component configuration failed.

To resolve this issue, check the configuration file based on the error code information. If the cause is not identified, you can ask a professional on the [Q&A page](https://ask.oceanbase.com/).

### OBD-1021: Component xxx is not in cluster

The error occurs because the component to be deleted does not exist in the cluster.

To resolve this issue, you can execute the `obd cluster edit-config` command to open the configuration file and check the component information in the cluster to confirm whether the component to be deleted exists.

### OBD-1022: Component xxx still depends by xxx, could not remove

The error occurs because the component to be deleted is depended on by another component in the cluster. obd does not support deleting a component that is depended on by another component.

To resolve this issue, you can execute the `obd cluster edit-config` command to open the configuration file and check the dependencies between components (the `depends` parameter).

### OBD-1023: Failed to merge config: xxx

The error occurs because the merging of the configuration file failed.

To resolve this issue, check the configuration file based on the error code information. If the cause is not identified, you can ask a professional on the [Q&A page](https://ask.oceanbase.com/).

### OBD-1024: The cluster will have no remaining components

The error occurs because the component to be deleted is the only component in the cluster.

To resolve this issue, if you want to delete all components in the cluster, you can execute the `obd cluster destroy` command to destroy the cluster.

### OBD-1025: ({ip}) {component} {key} invalid

The error occurs because the password configured for the component does not meet the requirements. obd checks the component based on the password requirements of the component. The specific password requirements are as follows.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>When you deploy OceanBase Database by using the graphical interface, the frontend page intercepts passwords that do not meet the requirements. Therefore, this topic only describes the password requirements for command-line operations. </p>
</main>

- The admin login password of the OCP console (`admin_password`) must meet the following requirements:

  - The length is 8 to 32 characters.

  - At least three types of the following characters are included: digits (0\~9), uppercase letters (A\~Z), lowercase letters (a\~z), and special characters (<code>~!@#%^&*_-+=|(){}[]:;,.?/$`'"<>\\</code>).

- The HTTP service authentication password of OBAgent (`http_basic_auth_password`) must meet the following requirements:

  - The length is in the range of [0, +∞).

  - Digits (0\~9), uppercase letters (A\~Z), lowercase letters (a\~z), and special characters (<code>~^*{}[]_-+</code>) are supported.

To resolve this issue, you can execute the `obd cluster edit-config` command to open the configuration file, modify the corresponding configuration item for the component in the configuration file, and save the changes. Then, copy and execute the restart command output by the CLI.

### OBD-1026: Could not modify {key} when the cluster is in the working status(`production_mode` is True, not support this operation)

The error occurs because the modification of the configuration item takes effect only after you execute the `obd cluster redeploy` command. This command destroys the cluster and deploys it again, which will result in data loss. Therefore, in a production environment (`production_mode=true`), you cannot modify a configuration item that takes effect only after a redeployment.

To resolve this issue, the `production_mode` parameter is set to `true` by default when you deploy an OceanBase cluster. If your cluster is not in a production environment and you can accept the risk of data loss, you can execute the `obd cluster edit-config` command to set the `production_mode` parameter to `false`, restart the cluster based on the output command, and then modify the configuration item again.

### OBD-1027: If you are sure the directory can be emptied, run `obd cluster deploy -f {deploy_name}` to perform forced deployment

The error occurs because the directory specified in the configuration file is not empty.

To resolve this issue, you can choose to empty the directory or configure a new empty directory. The specific methods are as follows:

- Empty the directory: You can manually empty the directory (the error code OBD-1002 will be output) or add the `-f` parameter to the deployment command to automatically empty the directory (copy the command output by the error code).

- Configure a new directory: You can execute the `obd cluster edit-config <deploy name>` command to open the configuration file and configure a new directory for the corresponding configuration item (the error code OBD-1002 will be output).

## OceanBase deployment errors

### OBD-2000: x.x.x.x not enough memory

Error cause: The available memory is insufficient.

Solution: The memory of obd is calculated based on MemAvailable. If you have cached memory that can be released, you can run the following command to release it.

```shell
sudo sysctl -w vm.drop_caches=1
# or
sudo echo 1 > /proc/sys/vm/drop_caches
```

If the memory is still insufficient, run the `obd cluster edit-config <deploy name>` command to open the configuration file and adjust the `memory_limt` and `system_memory` parameters. Generally, `memory_limt/3 ≤ system_memory ≤ memory_limt/2`.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <ul>
  <li>
  <p>When you deploy OceanBase Database 4.x before the current version, the value of <code>memory_limt</code> must be no less than 8 GB. In other words, the available memory must be no less than 8 GB. </p>
  </li>
  <li>
  <p>When you deploy OceanBase Database 4.x, the value of <code>memory_limt</code> must be no less than 6 GB. In other words, the available memory must be no less than 6 GB. </p>
  </li>
  </ul>
</main>

### OBD-2001: server can not migrate in

Error cause: The number of available units is less than `--unit-num`.

Solution: You can modify the `--unit-num` parameter. Run the following command to view the number of available units.

```sql
select count(*) num from oceanbase.__all_server where status = 'active' and start_service_time > 0
```

### OBD-2002: failed to start x.x.x.x observer

Error cause: This error can be caused by the following two reasons:

- The value of `memory_limit` is less than 8 GB.

- The value of `system_memory` is too large or too small. Generally, `memory_limt/3 ≤ system_memory ≤ memory_limt/2`.

Solution:

- If the error is caused by the two reasons above, you can adjust the corresponding parameters.

- If the error is not caused by the two reasons above, you can go to the [Q&A section](https://ask.oceanbase.com/) on the official website to ask questions. Professionals will provide answers.

### OBD-2003: not enough disk space for clog. Use redo_dir to set other disk for clog, or reduce the value of datafile_size

Error cause: The disk usage exceeds the specified threshold.

- If you use automatic deployment, the disk usage must be no more than 72%.

- If you use manual deployment, the disk usage must be no more than 64% without changing the configuration.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>If <code>redo_dir</code> and <code>data_dir</code> are on the same disk, the space that datafiles will occupy is included in the disk usage calculation. </p>
</main>

Solution: You can adjust the disk storage based on the deployment method. The following two methods are available.

- If you use command-line deployment, run the `obd cluster edit-config <deploy name>` command to open the configuration file, modify the disk-related parameters (such as `datafile_size`, `memory_limit`, and `log_disk_size`), save the changes, and then run the command output on the command line to make the changes take effect.

- If you use GUI deployment, click **<UI-TERM key="ocp-v2.Credential.Component.ImportModal.PreviousStep">Previous</UI-TERM>** to go to the **Cluster Configuration** page (when you deploy OceanBase Database) or the **<UI-TERM key="ocp-v2.Binlog.New.MetadbConfiguration">MetaDB Configuration</UI-TERM>** page (when you deploy OCP). Click **<UI-TERM key="ocp-v2.src.component.AddUnitSpecModal.MoreConfigurations">More Settings</UI-TERM>** in the **Cluster Configuration** section to modify the disk-related parameters (such as `datafile_size`, `memory_limit`, and `log_disk_size`).

### OBD-2004: Invalid: xxx is not a single server configuration item

Error cause: The modified parameter is a global parameter and cannot be modified for a single server.

Solution: You can move the parameter to the global section.

### OBD-2005: Failed to register cluster. xxx may have been registered in xxx

Error cause: The cluster registration failed, or the cluster has been registered.

Solution: First, check whether the `appname` parameter is configured. If the `appname` parameter is not configured, the cluster cannot be registered to obconfigserver. Then, handle the following two scenarios based on whether the cluster is deployed.

- Scenario 1: If you want to register an undeployed OceanBase cluster to obconfigserver, comment on the `obconfig_url` parameter, start the cluster, and then run the `obd cluster edit-config` command to configure the `obconfig_url` parameter. Currently, you cannot register an undeployed cluster to obconfigserver.

- Scenario 2: If you want to register a deployed cluster to obconfigserver, check whether the `obconfig_url` parameter is configured correctly.

  - If the `obconfig_url` parameter is not configured correctly, run the `obd cluster edit-config` command to open the configuration file and configure the correct Config URL for the `obconfig_url` parameter.

  - If you confirm that the `obconfig_url` parameter is configured correctly and want to force overwrite, add the `-f` parameter to the `obd cluster start` command to overwrite the registered cluster.

### OBD-2006: x.x.x.x has more than one network interface. Please set `devname` for x.x.x.x

Error cause: The server has multiple network interfaces, and obd cannot obtain the devname.

Solution: The following two methods are available based on the deployment method.

- If you use command-line deployment, run the `obd cluster edit-config <deploy_name>` command to open the configuration file, add or modify the `devname` parameter in the configuration file, save the changes, and then run the command output on the command line to make the changes take effect.

- If you use GUI deployment, click **<UI-TERM key="ocp-v2.Component.AddSamplingInspectStrategy.PreviousStep">Previous</UI-TERM>** to go to the **Cluster Configuration** page (when you deploy OceanBase Database) or the **<UI-TERM key="ocp-v2.Binlog.New.MetadbConfiguration">MetaDB Configuration</UI-TERM>** page (when you deploy OCP). Click **<UI-TERM key="ocp-v2.src.component.AddUnitSpecModal.MoreConfigurations">More Settings</UI-TERM>** in the **Cluster Configuration** section to set the devname.

### OBD-2007: x.x.x.x xxx fail to ping x.x.x.x

Cause: The ping command cannot be executed between the servers.

Solution:

1. Check whether the network is accessible between the servers.

2. Check whether the network configurations (`devname`/`local_ip`) match the actual configurations. You can run the `ip addr` command to view the correspondence between the IP address and the network card. If they do not match, you can modify the configurations based on the deployment method.

   - In command-line mode, run the `obd cluster edit-config <deploy_name>` command to open the configuration file. Add or modify the `devname` parameter in the file and run the command output in the command line to make the modification take effect.

   - In graphical interface mode, click **<UI-TERM key="ocp-v2.component.StepsMoveOutCluster.Step2.PreviousStep">Previous</UI-TERM>**. On the **Cluster Configuration** page (when you deploy OceanBase Database) or the **<UI-TERM key="ocp-v2.Binlog.New.MetadbConfiguration">MetaDB Configuration</UI-TERM>** page (when you deploy OCP), click **<UI-TERM key="ocp-v2.src.component.AddUnitSpecModal.MoreConfigurations">More Settings</UI-TERM>** in the **Cluster Configuration** section and set the devname.

3. If the error is `operation not permitted`, check the permissions of the ping file. You can run the `sudo chmod u+s /usr/bin/ping` command to modify the permissions of the ping file.

4. If the error is `No such file or directory`, it indicates that the ping command is not available in the environment. You can run the `sudo yum install iputils` or `sudo apt-get install iputils-ping` command to install the ping command.

### OBD-2008: Cluster clocks are out of sync

Cause: The clocks of the servers are out of sync.

Solution: Synchronize the clocks of the servers.

### OBD-2009: x.x.x.x: when production_mode is True, xxx can not be less then xxx

Cause: When the production mode is enabled, the `__min_full_resource_pool_mem` and `memory_limit` parameters cannot be less than the specified values.

Solution:

- In non-production environments, run the `obd cluster edit-config <deploy_name>` command to open the configuration file. Set the `production_mode` parameter to `False`, save the file, and run the command output in the command line to make the modification take effect.

- In production environments, run the `obd cluster edit-config <deploy_name>` command to open the configuration file. Set the `__min_full_resource_pool_mem` and `memory_limit` parameters to values greater than the specified values, save the file, and run the command output in the command line to make the modification take effect.

### OBD-2010: x.x.x.x: system_memory too large. system_memory must be less than memory_limit/memory_limit_percentage

Cause: The `system_memory` parameter is configured to a value that is too large. The value of the `system_memory` parameter must be less than the value of the `memory_limit` parameter or the value of the `memory_limit_percentage` parameter multiplied by the value of the `total_memory` parameter.

Solution: You can modify the `system_memory` parameter based on the deployment method.

     ```shell

     systemctl restart ntpd         # Restart the NTP service.
     ```

**Solution**: Run the `obd cluster edit-config <deploy_name>` command to open the configuration file and check whether the time series database configuration is correct. If the content is incorrect, update it based on the correct information.

### OBD-4703: ({ip}) {disk} not enough disk space

**Cause**: When you choose the **Online Upgrade** method to upgrade OMS, you need to specify a path to store the upgrade files. The disk space of the specified path is insufficient.

**Solution**: Configure a directory with sufficient disk space.

### OBD-4704: HA is enabled, please disable it before upgrade

**Cause**: Before you upgrade OMS, you must disable the High Available (HA) module. The HA module ensures the stability and continuity of data transmission links. For more information, see [OMS Community Edition HA](https://www.oceanbase.com/docs/community-oms-cn-1000000004253137) in the **OceanBase Migration Service** topic.

**Solution**: Disable the HA module before you upgrade OMS. Procedure:

1. Log in to the OMS Community Edition console.

2. In the left-side navigation pane, choose **<UI-TERM key="ocp-v2.src.util.menu.SystemManagement">System Management</UI-TERM>** > **<UI-TERM key="ocp-v2.page.Property.SystemParameters">System Parameters</UI-TERM>**.

3. On the **<UI-TERM key="ocp-v2.src.util.menu.SystemParameters">System Parameters</UI-TERM>** page, find `ha.config`.

4. Click the edit icon next to the **Value** field of the parameter.

5. In the **Modify Value** dialog box, set `enable` to `false` to disable the HA module.

## Error messages related to obdiag

### OBD-6000: Failed to execute obdiag command. You may not have installed obdiag.

Cause: The obdiag component is not installed.

Solution: You can install the obdiag component by running the following command:

```shell
obd tool install obdiag
source ~/oceanbase-diagnostic-tool/init.sh
```

### OBD-6001: obdiag must contain dependent components xxxx

Cause: The obdiag component is not installed. The obdiag service on obd is used to manage OceanBase or ODP clusters deployed through obd. If no OceanBase or ODP cluster is deployed on obd, this error will be reported.

Solution: Install the dependent components of obdiag, that is, register at least one OceanBase or ODP cluster on obd. You can run the `obd cluster list` command to view all clusters registered on obd.

### OBD-6002: obdiag options xxx format error, please check the value : xxx

Cause: The value of the parameter for the obdiag command is not in the correct format.

Solution: You can run the following command to view the parameters required for the obdiag command and pass the correct obdiag parameter format.

```shell
# example
obd obdiag gather -h

obd obdiag gather log -h
```

### OBD-6003: Failed to execute obdiag function xxx

Cause: The obdiag command fails to execute, which is likely due to the execution of a non-existent obdiag command.

Solution: You can run the following command to view the obdiag commands supported by obd.

```shell
obd obdiag -h
```
